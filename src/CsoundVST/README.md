# Csound Visual VST3

A VST3 plug-in (Windows x64, C++20) that runs the **Csound 7** engine inside a DAW
(tested with the Steinberg validator and an automated test host; target host: Cubase 15).
One module, `CsoundVisual.vst3`, contains two classes (vendor **Csound Visual**):

| Class | Category | Busses | Class ID |
|---|---|---|---|
| **Csound Visual Instrument** | `Instrument\|Synth` | MIDI in → stereo out | `82E53EA5-F47D4F4A-9641FC59-93A8CD51` |
| **Csound Visual FX** | `Fx` | stereo in + MIDI in → stereo out | `210C3013-BA8B4347-ACE9B078-3FB37C5C` |

The class IDs are fixed: Cubase projects reference the plug-ins by them, never change them.

The plug-in has **no custom editor**. Cubase shows its generic parameter editor
(16 sliders named after the orchestra's channels). The CSD itself is written in the
Csound Visual app and sent to a running plug-in instance over a named pipe (see *IPC*).

## Build

Requirements: Visual Studio 2022 or newer (C++ workload; the script finds it with
`vswhere`), CMake ≥ 3.25, Ninja, git, and a Csound 7 copy in `@Source\Csound7` (see
*Bundle layout*).

```powershell
powershell -ExecutionPolicy Bypass -File tools\build_vst.ps1
```

The script (project root `tools\build_vst.ps1`):

1. clones the Steinberg VST3 SDK (MIT) into `src\CsoundVST\external\vst3sdk` if missing;
2. loads the VS x64 environment (`vcvars64.bat`), configures CMake + Ninja (Release) into
   `src\CsoundVST\build` and builds `CsoundVisual`, the SDK `validator` and `vsthost_test`;
3. runs the validator and `vsthost_test` on the bundle (skip with `-SkipTests`);
4. copies the bundle to `src\CsoundVST\dist\` and installs it into the per-user VST3 folder
   `%LOCALAPPDATA%\Programs\Common\VST3\CsoundVisual.vst3` (skip with `-NoInstall`).
   Close Cubase first: Windows locks a loaded plug-in DLL.

Other switches: `-Clean` (delete the build folder first), `-Config Debug`.

Manual build:

```powershell
cmake -S src\CsoundVST -B src\CsoundVST\build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build src\CsoundVST\build --target CsoundVisual validator vsthost_test
src\CsoundVST\build\bin\validator.exe src\CsoundVST\build\VST3\Release\CsoundVisual.vst3
src\CsoundVST\build\bin\vsthost_test.exe src\CsoundVST\build\VST3\Release\CsoundVisual.vst3
```

The SDK is configured lean: no VSTGUI, no example plug-ins or hosts
(`SMTG_ENABLE_VSTGUI_SUPPORT`, `SMTG_ENABLE_VST3_PLUGIN_EXAMPLES`,
`SMTG_ENABLE_VST3_HOSTING_EXAMPLES` = OFF), no symlink into `C:\Program Files`
(`SMTG_CREATE_PLUGIN_LINK` = OFF) and the static CRT (`/MT`), so the plug-in does not depend
on a VC++ redistributable inside the DAW.

## Architecture

### Engine

Each plug-in instance owns at most one running `CsoundInstance`. Building one (on a
non-audio thread):

1. `csoundCreate(hostData, <bundle>\Resources\Csound7\plugins64)`; message callback;
   `csoundSetHostAudioIO` (Csound never opens an audio device); `csoundSetHostMIDIIO` plus
   the external MIDI in callbacks.
2. The CSD is preprocessed (`prepareCsd`):
   * `<CsOptions>` is parsed; options that make no sense in a plug-in are dropped and logged
     (`-o…`, `-i…`, `-n`, `-r`, `--sample-rate`, `--nchnls*`, `-b`/`-B`, `-M…`,
     `-+rtaudio`, `-+rtmidi`, `--midi-device`, `-F`, `-L`, `-U`, …). Harmless options such as
     `--midi-key=4 --midi-velocity-amp=5` or `--omacro:` are kept. The section is then
     emptied so it cannot override the plug-in's options.
   * `f0 z` is inserted at the top of `<CsScore>` (or a score is added) so the performance
     never ends inside the DAW.
   * Plain orchestra text without CSD tags is wrapped into a CSD.
3. Options, each passed separately (`csoundSetOption` splits on spaces):
   kept user options, then `-n -d -m0 -M0 --nchnls=2 --nchnls_i=2 --sample-rate=<host sr>`.
   `--sample-rate` overrides the `sr` of the orchestra header (verified by the test: a CSD
   with `sr = 44100` runs at 48000); **ksmps is kept from the CSD**.
4. `csoundCompileCSD(text, mode 1)`, `csoundStart`.
5. Channels: `csoundListChannels` → every *input control* channel except `HOST_*`. They are
   ordered by their declaration order in the source (`chnk` / `chn_k` / `chnexport`), then
   any other input channels by name. The first 16 are assigned to the parameter slots.
   Channel pointers are cached (`csoundGetChannelPtr`), and the `HOST_BPM`, `HOST_PLAYING`,
   `HOST_PPQ`, `HOST_SR` channels are created now, so the audio thread never allocates.

**Audio (spin/spout):** for each host frame the input is written to `spin[pos]` (×0dbfs),
the output read from `spout[pos]` (÷0dbfs) and `pos` advanced; when `pos == ksmps`,
`csoundPerformKsmps` runs. Any host block size works (tested: 1…512, 333, 0, and blocks
larger than `maxSamplesPerBlock`, which are processed in chunks), and the
plug-in has a constant latency of exactly **ksmps** frames, reported through
`getLatencySamples()` (a change triggers `restartComponent(kLatencyChanged)`). Mono
orchestras (`nchnls = 1`) are duplicated to both outputs. NaN/Inf/absurd samples are
replaced by silence. If the score ends or Csound reports an error the instance outputs
silence until the next load. `getTailSamples()` returns `kInfiniteTail` so Cubase never
cuts reverb/delay tails.

**MIDI:** VST3 note-on/off and poly pressure events become MIDI 1.0 bytes (velocity
0..1 → 1..127). Pitch bend, CC1 (mod wheel), CC2 (breath), CC11 (expression), CC64
(sustain) and channel aftertouch arrive through `IMidiMapping` as hidden parameters, one set
per MIDI channel (ids 100…105 for channel 1, 300…389 for channels 2…16:
`300 + (channel−2)·6 + index`), and are converted back to MIDI on the channel they came
from. Events are
merged and sorted by sample offset; the block is rendered in segments so every event
enters Csound in the control cycle of its frame. Csound reads them in its MIDI read
callback (`massign`, `cpsmidi`, `notnum`, `veloc`, `pchbend`, `midictrl`… all work).

**Host info:** every block the plug-in writes `HOST_BPM` (tempo), `HOST_PLAYING` (0/1),
`HOST_PPQ` (musical position in quarter notes) and `HOST_SR` into Csound channels; read
them with `chnget:k("HOST_BPM")` etc.

**Bypass:** parameter id 200 (`kIsBypass`). Csound keeps running; the FX outputs the dry
input delayed by the latency (so delay compensation stays exact), the Instrument outputs
silence. The bypass state is saved with the plug-in state.

### Parameters

* `Param 1`…`Param 16` (ids 0…15), normalized 0..1, automatable. After every compile they
  are renamed to the orchestra's channel names; unused slots are titled `—`. The host is
  told with `restartComponent(kParamTitlesChanged | kParamValuesChanged)`.
* Normalized ↔ channel value uses the channel hints: `min + n·(max−min)` (linear, type 2),
  `min·(max/min)^n` (exponential, type 3, min > 0), rounded for integer (type 1); channels
  without hints map 0..1. The generic editor shows the real value
  (`getParamStringByValue`) and accepts typed values.
* After a `load` from the app the parameters jump to the channel defaults (`idflt` of
  `chnk`); after loading a Cubase project they keep their saved values.
* Every block, each assigned slot is written to its channel (`chnget` sees it at the next
  control cycle).

Declare channels like this (name, mode 1 = input, type, default, min, max):

```csound
chnk "cutoff", 1, 3, 2400, 80, 16000   ; exponential
chnk "mix",    1, 2, 0.35, 0, 1        ; linear
kcut chnget "cutoff"
```

### State

`getState`/`setState` (binary, little-endian, versioned):
`magic "CSVV"`, `version` (2), `kind` (0 instrument / 1 FX), `csdName`, `csd text`
(int32 length + UTF-8 bytes), `count` + `count` doubles (the 16 normalized parameter
values), `bypass` (int32, since v2). Readers ignore extra trailing fields, strings are
length-checked, a broken stream is rejected, and so is a state whose `kind` is not the
loading class (an Instrument chunk in the FX or the reverse). A Cubase project therefore restores the
orchestra and its parameter values; if the saved CSD no longer compiles, its text is kept
(so it is not lost on the next save) and the error is in the status log.

### Threading model

| Thread | What it does |
|---|---|
| Host UI thread | `initialize`, `setActive`, `setState`, `getState`, parameter queries; runs the hidden message-only window that applies parameter renames, `restartComponent` and `performEdit` |
| Host audio thread | `process()` only: never allocates, never blocks |
| IPC thread (one per instance) | named-pipe server; compiles new orchestras for `load` |

* **Swap protocol.** A new `CsoundInstance` is created, compiled and started completely on
  the IPC (or UI) thread. It is published by swapping a `unique_ptr` under `swapMutex`;
  the audio thread only ever `try_lock`s that mutex and outputs one block of silence if it
  is busy, it never waits. The previous instance is then destroyed on the loading thread.
  A failed compile leaves the running orchestra untouched.
* `lifetimeMutex` (never touched by the audio thread) serializes everything that creates,
  destroys or inspects instances: `setActive`, `setState`, IPC `load`/`status`/`set`.
* Parameter values are `std::atomic<double>`; channel values are written through the cached
  Csound channel pointers with 8-byte atomic stores (`std::atomic_ref`).
* MIDI uses a lock-free SPSC byte FIFO (producer `process()`, consumer Csound's MIDI read
  callback inside `csoundPerformKsmps`, same thread).
* Csound messages printed on the audio thread go to a lock-free FIFO, drained into the
  200-line log by the IPC thread (`load`, `status`) and before every rebuild; messages on
  other threads go straight to the log (short mutex).
* Anything for the host UI is posted to the hidden window (`PostMessage`), or applied
  directly when already on the UI thread — never while holding `lifetimeMutex`, because
  `restartComponent` may call back into the plug-in.

## IPC protocol (Csound Visual app ↔ plug-in)

### Discovery

While an instance exists it keeps a descriptor file

```
%LOCALAPPDATA%\CsoundVisual\vst-instances\<pid>.<instanceCounter>.json
```

```json
{"pipe":"\\\\.\\pipe\\CsoundVisualVST.12345.1","pid":12345,"kind":"instrument",
 "track":"Csound Pad","csdName":"default","host":"Cubase"}
```

* `kind`: `"instrument"` or `"fx"`; `track`: the Cubase track name
  (`IInfoListener::setChannelContextInfos`, empty until the host sends it);
  `csdName`: name of the loaded CSD or `"default"`; `host`: `IHostApplication::getName`.
* Rewritten atomically (temp file + rename) when the track name or the CSD changes,
  deleted when the instance is terminated. Files of processes that no longer run (host
  crash) are deleted the next time the plug-in is loaded into a process (once per process,
  by its first instance); clients should still ignore files whose `pid` is not alive.

### Transport

* Pipe `\\.\pipe\CsoundVisualVST.<pid>.<instanceCounter>`, byte mode, local clients only.
* **One request per connection.** Client: connect, write the request, read the reply, close.
* Framing both ways: **4-byte little-endian length + UTF-8 JSON**.
* The first pipe instance is created with `FILE_FLAG_FIRST_PIPE_INSTANCE`, so the plug-in never
  joins a pipe name another process created first. The request body buffer grows as data
  arrives (64 KiB chunks, 64 MB cap), so a length header alone allocates nothing.
* The server serves connections one after another; a second listening instance exists while
  one is served, so a client never gets "pipe not found" between requests (it may get
  `ERROR_PIPE_BUSY` — wait and retry). I/O timeout on the server side: 10 s.

### Requests

**load** — compile a new orchestra (on the IPC thread) and swap it in.

```json
{"cmd":"load","name":"pad.csd","csd":"<CsoundSynthesizer>…</CsoundSynthesizer>"}
```
```json
{"ok":true,"log":"<Csound messages of this compile>","channels":["cutoff","resonance"]}
```
On failure: `{"ok":false,"log":"…","channels":[],"error":"Csound compilation failed (code 255)"}`
and the previous orchestra keeps playing. `channels` lists all input control channels in
slot order (the first 16 are the parameters).

**status**

```json
{"cmd":"status"}
```
```json
{"ok":true,"kind":"instrument","track":"Csound Pad","host":"Cubase","csdName":"pad.csd",
 "csound":"Csound 7.0.0 loaded from …","pipe":"\\\\.\\pipe\\…","active":true,
 "sr":48000,"ksmps":32,"running":true,
 "channels":[{"name":"cutoff","min":80,"max":16000,"default":2400,"value":2400,"param":1}],
 "log":"<last ~200 lines>"}
```
`param` is the 1-based parameter slot (0 = not mapped); `value` is the current value in
channel units.

**set** — set a channel by name.

```json
{"cmd":"set","channel":"cutoff","value":1234.5}
```
```json
{"ok":true}
```
If the channel is mapped to a parameter, the parameter moves too (the host is told with
`performEdit`, so it behaves like a user edit and can be recorded as automation); unmapped
channels are written directly. Unknown channel → `{"ok":false,"error":"unknown channel: …"}`.

Unknown command or invalid JSON → `{"ok":false,"error":"…"}`.

## Csound location

At first use the plug-in loads `csound7_64.dll` with
`LoadLibraryExW(<full path>, LOAD_WITH_ALTERED_SEARCH_PATH)` and resolves every API
function with `GetProcAddress` (no import library), trying in order:

1. the private copy in the bundle: `<bundle>\Contents\Resources\Csound7` (found from the
   plug-in's own module handle, `GetModuleHandleExW` with a function address);
2. `%CSOUND_VISUAL_HOME%` (the Csound root itself, or a folder containing `Csound7` or
   `@Source\Csound7`);
3. `C:\Program Files\Csound7`.

It checks that the build uses 64-bit doubles, sets `SADIR`/`SSDIR` to `samples\` and
`OPCODE7DIR64` to `plugins64\` (`csoundSetGlobalEnv`), and calls `csoundInitialize` with
`CSOUNDINIT_NO_SIGNAL_HANDLER | CSOUNDINIT_NO_ATEXIT`. If Csound cannot be loaded the
plug-in still loads in the host, outputs silence and reports the reason in `status`.

## Default orchestras

* **Instrument — "Velvet Poly":** per voice two detuned saws, a saw one octave up and a
  triangle sub one octave down,
  `moogladder2` low-pass with velocity/envelope sweep, ADSR; shared stereo chorus and a big
  `reverbsc`; soft `tanh` safety limiter. Pitch bend ±2 semitones, mod wheel vibrato, CC11,
  sustain. Channels: `cutoff`, `resonance`, `attack`, `release`, `reverb`, `volume`.
* **FX — "Wide Echo Space":** modulated ping-pong delay whose repeats darken (`tone` in the
  feedback path), chorus on the echoes, `reverbsc` fed by dry + echoes, dry/wet mix.
  Channels: `mix`, `time` (s), `feedback`, `tone` (Hz), `size`.

Edit `resource/default_*.csd` and rebuild to change them (they are embedded as string
literals by CMake).

## In Cubase

1. Close Cubase, run `tools\build_vst.ps1` (or copy `dist\CsoundVisual.vst3` into
   `%LOCALAPPDATA%\Programs\Common\VST3\`).
2. Start Cubase. If the plug-ins do not appear: *Studio > VST Plug-in Manager*, check that
   `C:\Users\<you>\AppData\Local\Programs\Common\VST3` is in the VST 3 paths, then
   *Rescan*.
3. **Csound Visual Instrument**: add an Instrument track, *Instruments > Csound Visual >
   Csound Visual Instrument* (category Synth). Play MIDI: the default patch sounds at once.
4. **Csound Visual FX**: insert slot of an audio track, *Csound Visual > Csound Visual FX*.
5. The parameters appear in Cubase's generic editor and automation lanes under the
   channel names. Load your own orchestra from the Csound Visual app (it finds the instance
   through the descriptor file and sends `load`).

## Known limitations

* No custom GUI (generic editor only); orchestras are edited and sent from the Csound
  Visual app.
* Stereo only (one stereo output bus, one stereo input bus for the FX); 32-bit float
  processing (Csound itself computes in double).
* Latency = ksmps frames (keep ksmps small, e.g. 16–64).
* Parameter changes are applied once per host block (not sample-accurate); channel
  values reach Csound at the next control cycle.
* MIDI CC other than 1, 2, 11, 64, pitch bend and aftertouch are not forwarded (VST3
  delivers controllers only through IMidiMapping parameters).
* Orchestras that end the performance themselves (`e` in the score, `exitnow`) go silent
  until the next load. Score time starts when the instance is built, not with the DAW
  transport (use `HOST_PPQ` / `HOST_PLAYING` for sync).
* File paths in an orchestra (soundin, GEN01…) should be absolute: the DAW's working
  directory is unrelated to the CSD's folder.

## IPC addendum: `meters`

`{"cmd":"meters","samples":N}` (64 ≤ N ≤ 4096) → `{"ok":true,"sr":<host rate>,"peaks":[L,R],"scope":[N newest samples of the mono mix]}`.
The audio thread keeps the per-channel peak since the previous request and a 4096-sample ring of the
output (mono mix); the pipe thread takes the peaks (resetting them to 0) and copies the ring. The
Csound Visual app polls this ~25 times per second while linked and shows it in its «VST3 OUTPUT» card.
